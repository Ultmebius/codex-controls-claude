# Codex Controls Claude

A local Codex plugin combining a stdio MCP, orchestration skills and diagnostic scripts. Codex owns planning and independent acceptance; Claude Code executes scoped tasks using your configured model.

Explicitly invoke this plugin or its `orchestrate` skill to activate Claude Code assistance. Generic coding requests do not activate it. Authorized follow-ups may continue the same run. The MCP records task dependencies and contracts, waits for actionable SDK events, reruns independent acceptance checks, records rework and unlocks accepted dependencies.

Prerequisites: Node 22+, local Claude Code, Windows Git Bash where applicable, and existing authorized Claude Code authentication or gateway settings. Model selection reads `~/.claude/settings.json` `env.ANTHROPIC_MODEL` first, then existing environment or top-level `model`, otherwise the native Claude Code default. Warm sessions keep their startup model; close/resume or start a new session to apply a model change. Run the setup skill or `node scripts/doctor.mjs` to diagnose prerequisites. Local gateway credentials are loaded at runtime and are not included in this package.

Codex can explicitly schedule one to three Claude Code workers. Use the ordinary plan for one worker or `orchestrator_team` for independent parallel tasks. Teams reserve literal write scopes or separate workspaces, enforce dependencies and share a persistent turn allowance. Defaults: 500 native agentic rounds per segment, 1000 SDK-reported turns per run/team, two hours per execution segment/run, and two acceptance repairs. Budget continuation, interruption recovery and acceptance rework have separate counters. Explicit interruption requests a native result before bounded fallback termination. Every execution records confirmed/provisional/reserved accounting and default/requested/effective caps. Unknown charges are conservative allowances, not observed turns or token counts. Follow-ups never reset the budget.

Assign a short human role name per worker: `workerName` on `orchestrator_plan(action="create")` or on each `orchestrator_team` task. It is a task and audit label, not the window caption: Claude Code owns the visible terminal title, and the dashboard conversation name comes from the task heading. Without a name the first task title is used. The label is display-only, sanitized, persisted with the run, and never changes contracts, prompts or native behavior. The launch-time spawn title is a private nonce that is never displayed; ownership is verified by HWND, PID and that private identity, so equal display names stay distinct and a user rename can never strand an owned window.

On Windows each actual Claude Code execution process is hosted in its own dedicated minimized Windows Terminal with an independent C# dashboard: model, native permission mode, workspace, tools, review/failure status, elapsed runtime and effort. Terminals never aggregate state across workers, and each dashboard reports only its own session. Effort is labelled configured unless authoritative native metadata confirms it; unconfirmed effort stays unknown and must not be guessed high. Conversation selectors appear only when that single terminal has actually shown more than one native conversation ID; task stages, retries and peer workers are not conversations, and a single-conversation terminal shows no redundant tab strip. The dashboard invents no new-chat control and cannot manufacture a native session. This is an event-driven view of the SDK session; interaction and acceptance happen through Codex. It does not start a second interactive Claude process. Closing it stops only that worker. Windows Terminal and .NET10 are required; the packaged compiled helper owns transport and native window control.

Warm tasks reuse a live SDK session. After technical acceptance the candidate waits for user review; the supervisor retains it for useful follow-up or closes it with its transcript preserved. Human approval completes the run and closes the worker. Idle review sessions suspend after 30 minutes. Saved sessions resume on the next explicit task.

Normal output is compact with explicit truncation markers and targeted evidence retrieval; full blockers, errors, hashes and checks remain retrievable. Context alarms use the latest response's reported context usage from the SDK stream, or one local SDK transcript read at completion when stream usage is absent. Unknown usage is null. No transcript polling is used. Thresholds: consider compact/new around300K, maintain before400K, with smaller limits for smaller reported windows. New contexts carry a deterministic supervisor checkpoint.

Execution capacity is exactly three active executions shared across all connected chats, ordinary runs and team children; a fourth is rejected until an owned one finishes, and retained idle transcripts consume no slot. Ownership stays per run: another chat can never take over a live run.

`orchestrator_wait` uses one pending event-triggered promise, defaulting to and capped at20 minutes (1200000ms). Completion, questions, residual permissions, failures, budget risk and cancellation wake it immediately; ordinary milestones stay in audit. A full idle20-minute call also needs the host MCP tool timeout above1200s: portable `mcp.json` stays schema-valid and cannot carry a timeout, while the installed Codex compatibility projection declares `tool_timeout_sec=1260` and `CCC_WAIT_MS=1200000`. A host that reports a shorter bound requires passing a shorter `timeoutMs`; that limit is honest configuration evidence, not a reason to poll. The skill's bounded same-connection wait chain renews empty waits without status/log inspection. This reduces unnecessary wakeups but does not establish measured token savings or wake a closed chat.

The package includes a built server and its maintained source subset under `server/source`. Development checkout, dependencies, test fixtures and reports are maintained in the surrounding workspace. See `UPSTREAM.md` and `THIRD_PARTY_NOTICES.md` for provenance and licenses.

Native tools and the user's enabled Claude MCP configuration are inherited. The plugin disables no native tool: subagents (Agent/TeamCreate/TeamDelete/Task) follow the user's own Claude Code settings and permissions, while the three-execution ceiling applies only to the top-level workers Codex dispatches. Dispatch instructions describe the task rather than assuming supervisor tool names. Sanitized actual capabilities distinguish pending/connected servers; relevant native config changes reload the saved conversation at task boundaries. No Codex MCP configuration or credentials are copied.

Each query receives a fresh in-process `codex_supervisor` MCP server. Claude calls `notify_supervisor` for audited milestones or `ask_supervisor` for decisions, which wakes the wait. Codex answers inside the original worker tool call. Native `AskUserQuestion` uses the same event channel: Codex receives the original questions and options as a `worker_question` and replies with `{"answers":{"<exact question text>":"<label or free text>"}}` (a single question also accepts plain text; multi-select may send a JSON array of labels). The native tool then continues with its original `updatedInput` plus `answers`, without creating an ordinary permission record. Timeout, cancellation, reset, a stale ID or an incomplete/unparseable reply rejects the question explicitly, so the worker reports BLOCKED rather than guessing. Default decision expiry is five minutes; CCC_DECISION_TIMEOUT_MS configures1s..30min. Expired decisions remain recorded; explicit continuation re-evaluates current input, never replays an old approval. No extra daemon or global Claude MCP configuration is required.

Native permissions inherit effective user/project/local `permissions.defaultMode`. Auto mode uses Claude's classifier; bypass avoids ordinary supervisor approvals. User hooks and native deny/ask rules are untouched. The plugin adds no tool hooks, file gates, path rewriting/vetoes or default prohibition on worker validation. Native residual ask inputs are passed through unchanged. No native tool is blocked by the plugin; subagents and team tools follow the user's own Claude Code permissions and deny/ask rules. Write scopes are scheduling/audit contracts, not execution isolation; use separate worktrees/workspaces for potentially overlapping writes.

Guidance can reach a worker while it is mid-turn through one `orchestrator_message` schema. `action="queue"` (`runId`, stable `requestId`, `text`) is accepted immediately as `queued` and delivered as exactly one user input at the next native result boundary of the same conversation, FIFO across messages, with the follow-on segment reserved from the persistent turn budget before any input is written; an exhausted allowance fails it with `turn_budget_exhausted` instead of delivering late. `action="interrupt"` additionally asks the native runtime to end the current turn and returns `interruption_requested`; once that segment drains, the message is delivered into the same saved native conversation ahead of still-unsent queued messages, which stay `queued`. A changed native turn allowance cold-resumes that same session for the follow-on turn; the conversation ID and task contract never change. `action="reply"` (or omitting `action`) answers a pending `worker_question` with `messageId` and `answer` as before. Reported states are transport truth only — `queued`, `interruption_requested`, `delivering`, `delivered`, `failed`, `cancelled` — and `delivered` never claims the model read the text. Limits are 8 unsent messages, 32 accepted guidance records per run and 4000 characters per message; unsent guidance is never replayed after a restart. Team events carry childRunId, which routes existing review/status/permission/message tools. Dispatch team children only through the coordinator so budgets, scopes and capacity remain enforced. Review checks wait for overlapping workspaces to become quiescent; checks are serialized by the server. Use separate Git worktrees for overlapping changes and explicitly integrate accepted results; worktree creation does not copy uncommitted main-workspace edits. Teams currently use fixed DAGs; append/update/supersede and compaction remain single-run features. For team context maintenance, use child `sessionAction=new` to carry a checkpoint, then explicitly dispatch through the same team budget.

`dispatch(mode="continue")` resumes a budget-stopped task with its original contract. `plan(action="reconcile")` captures supervisor-completed current artifacts without model replay; normal review executes the original checks once. `status(sections=["result","checks","artifacts"])` returns targeted evidence without repeated contract/usage. Full evidence remains available. Verification may finish after the model-execution deadline.

Use `plan(action="attach",runId)` or team action=attach after connection loss. Diagnostic construction is read-only; recovery refreshes the ledger under an atomic claim and refuses live unreleased owners. Clean shutdown stops owned workers then releases ownership. Unique owner identities/generations fence stale writes. Idle connections release the shared execution lease. Original checks, revisions, dependencies and budgets survive recovery.

Git change inventories include untracked files and compare against the original task baseline even if edits are committed. Review detects undeclared changes. `include_artifacts` explicitly acknowledges necessary in-scope paths without weakening checks; acceptance hashes cover the extended set. Additional sections `changes`, `executions` and `decisions` expose precise evidence. Non-Git/unavailable inventories are explicitly unknown and still require supervisor diff review.

See the [worker policy inventory](skills/orchestrate/references/worker-policy.md) for native behavior and retained orchestration controls. Startup handshake defaults120s (CCC_INIT_TIMEOUT_MS); fixed-check review defaults5min (CCC_CHECK_TIMEOUT_MS). Each allows1s..10min. These transport/verification guards do not filter Claude tools or hooks.
