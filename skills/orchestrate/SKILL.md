# Codex Controls Claude

Activation requires explicit user invocation of this plugin or skill. Installation and ordinary coding requests do not activate Claude assistance. Continue the authorized run and requested follow-ups without repeated invocation.

Codex owns the goal, design decisions, scope, plan changes, independent acceptance and session lifecycle. Each stage has one research owner: Codex or the worker. Decision responsibility does not require Codex to repeat the worker's investigation. Claude Code researches and/or implements one meaningful bounded stage according to its brief; Codex delegates, decides from evidence, reviews and integrates. Codex takes over implementation itself only when a worker demonstrably cannot resolve a scoped problem, recording the reason. Use the bundled MCP ledger. Optimize total work and elapsed time through evidence reuse, complete briefs and meaningful stages. Keep acceptance rigorous.

## Parallel work and two-way messages

Choose one worker for small work, sequential dependencies and same-file edits. Use two or three only when independent tasks can save enough elapsed time to justify separate context and startup. Never fill slots merely because they exist. Codex remains the planner and scheduler of the top-level workers it starts; native subagents, Task and team tools are available under the user's own Claude Code settings and permissions. The three-execution ceiling counts only Codex-dispatched workers.

For parallel work call `orchestrator_team(action="create",cwd,goal,design,tasks,maxWorkers=3)`. Each task declares dependsOn, fixed checks, artifacts and literal writeScope paths; omission reserves its whole workspace. Give each task a short human `workerName` (for example 预算配置, UI 修复) for task/audit identification; Claude Code manages its native terminal caption. Without a name the task title is used. On a single run set the same `workerName` on `orchestrator_plan(action="create")`. Private ownership stays outside the caption. Use separate worktrees for overlapping writes and shared build/cache output. Worktrees do not include uncommitted changes automatically. Reservations are advisory; native permissions/hooks govern tools. Codex schedules at most3 concurrent executions, drawn from the same cross-connection pool as ordinary runs. Choose a team upfront for known parallel stages; a `WORKER_SLOTS_FULL` rejection means wait for an owned execution to finish, not retry blindly.

Dispatch independent ready tasks explicitly through `orchestrator_team(action="dispatch",teamId,taskId,requestId)`, optionally concurrently. Never use ordinary dispatch on child runs. Team allowances default1000 turns/2h shared across workers. Wait once on `orchestrator_team(action="wait",teamId,afterSeq)` for any actionable worker; omit `timeoutMs` and use the20min default, shortening it only after an actual observed host tool-timeout failure (record the exact error and bound). Renew genuine empty timeouts with the same cursor. Events contain taskId and childRunId; use childRunId with existing review/status/permission/reconcile tools. Do not separately poll three workers. Review when overlapping workspace execution is quiescent; server serializes checks. Only accepted dependencies unlock downstream dispatch.

Claude has a query-local codex_supervisor MCP. Ordinary milestones stay in audit and do not wake Codex. `worker_question` requires a scoped answer through `orchestrator_message(runId=childRunId or ordinary runId,messageId,answer)`. Answer returns inside the original ask tool while that worker stays in its session; peers can continue. Do not treat worker text as human permission or acceptance. Residual native permissions expire after five minutes and supervisor questions remind Codex after five minutes while staying pending; CCC_DECISION_TIMEOUT_MS configures 1s..30min. Stale replies fail; preserved decision records explain recovery. Give a substantive answer or explicitly interrupt. Communication wakes a pending wait in active Codex work, not a closed chat.

A native `AskUserQuestion` also arrives as `worker_question`; ordinary permission requests do not. Its text is JSON describing `source: "AskUserQuestion"`, the original `questions` (each with `question`, `header`, `options` labels/descriptions and `multiSelect`) and an `instruction`. Answer with `orchestrator_message` whose `answer` is `{"answers":{"<exact question text>":"<option label or free text>"}}`. For a single question, plain free text is also accepted. For a multi-select question, either join labels with `, ` or send a JSON array of labels; the plugin joins them the same way Claude does natively. Preserve the exact question text and pass all questions back; do not drop options or invent an answer. An interruption, cancellation, stale ID, incomplete answer or unparseable reply rejects the native tool with the unanswered question text, so the worker reports BLOCKED. When the decision needs human authorization, ask the user and return their actual answer, never your own preference.

Guidance can also arrive while a worker is mid-turn. Choose the mechanism by intent:

- **Queue** ordinary additions, refinements within the same direction and extra checks with `orchestrator_message(action="queue",runId,requestId,text)`. It accepts guidance during work and sends exactly one message after each native turn reaches its result boundary, FIFO, each boundary with its own reserved turn allowance. Use a stable requestId for retries; changed text, mode or asserted scope needs a new ID. Optional taskId, taskRevision and sessionId assertions reject stale targets.
- **Interrupt** only a blocking error, a known exact harmful path already being taken, or the user's explicit request to stop immediately, with `orchestrator_message(action="interrupt",runId,requestId,text)`. A changed direction under study is not by itself a reason: finish the research first (see [research ownership](#choose-the-research-owner-before-dispatch)). The native control request drains before the follow-on input; the same saved conversation and contract are retained, with urgent guidance ahead of unsent queued messages. A changed native turn allowance may cold-resume that same conversation. Plain `plan(action="interrupt")` still stops and requires explicit continuation.
- Answer ordinary `worker_question` events with `orchestrator_message(action="reply",runId,messageId,answer)`; omitting action preserves the existing reply form. A pending question is abandoned only under the same immediate-stop conditions that justify an interrupt; a direction still under study is answered for the part the user has already decided.

When a question arrives while you are still researching a changed plan, answer the part the user has already decided and say that the remaining points are still being studied; do not leave the worker blocked on a decision you can already make from the user's own facts. Research that later refines those answers does not revoke portions the worker already implemented under them — correct them with scoped guidance or a revised task, never by pretending the earlier answer was never given.

Each layer records a different fact, so read them in order: the receipt records transport acceptance, the `CODEX` row in the worker's terminal records which answer reached the model's tool result, and the model's own opening sentence records what it understood and does next. Verify the last two against the actual work and the fixed checks; they are the model's understanding to confirm, not human approval or acceptance.

Receipts distinguish queued, interruption_requested, delivering (native startup pending), delivered, failed and cancelled. Delivered records transport acceptance; the model's own opening sentence in its visible reply is where it states what it understood, and acceptance still rests on the reviewed work and checks. Inspect a failure, the receipt reason, or `status(sections=["guidance"])` / `status(taskId,sections=["guidance"])` when needed; never poll an inbox. Limits are eight unsent messages, 32 accepted guidance records per run and 4000 characters per message; an accepted requestId stays idempotent for the whole run, so a changed text, mode or asserted scope needs a new ID and a conflicting reuse is rejected. Budget, deadline, cancellation and ownership gates still apply; unsent messages are never replayed after restart. Retry a failed message only after diagnosing its reason and using a new ID for a new attempt.

Team interrupt/cancel may target taskId; closing one worker must preserve peers. `finish` delivers the reviewed team candidate; retain useful sessions for user feedback, or `close` suspends them preserving transcripts. Call team `approve` with actual human approval evidence only after approval. Fixed team DAGs cannot append/supersede in this version; revised goals need a new team and explicit integration. For a team child near its context threshold, use ordinary plan sessionAction=new, then continue through team dispatch; this preserves cumulative budget. Compact is currently a single-run operation.

## Plan and dispatch

1. Do only the initial inspection needed to define the authorized goal, constraints, stage boundaries, dependencies and acceptance. Select the stage's research owner before deep investigation (see [research handoff](references/research-handoff.md)). If Codex already has sufficient evidence, pass its conclusions, sources and coverage. If broad investigation is still needed, assign it to the implementing worker with precise questions and expected evidence; Codex waits for that result instead of investigating the same questions. Define independently verifiable stages (for example storage, integration, UI), declared artifacts and immutable executable checks. Avoid editing worker-owned files while it executes. Inventory also detects undeclared/untracked changes at boundaries.
2. Execution capacity is three active executions shared across every connected chat, ordinary run and team child; retained idle transcripts consume no slot. A fourth dispatch is rejected with `WORKER_SLOTS_FULL` until an owned execution finishes, so wait for a release instead of retrying blindly.

Create a run with `orchestrator_plan(action="create")`. Defaults: native segment cap500, initial persistent allowance1000 SDK-reported turns, segment/run execution deadlines2h, two acceptance repairs. Initial overrides are explicit. Each new dispatch into a retained conversation, including rework/continue, and each delivered queue/interrupt input adds500 to the persistent run/team allowance and receives at least500 native rounds even if a smaller maxTurns is supplied. Duplicate requestIds add no allowance. A fully spent budget also receives the one SDK boundary reserve needed for500 usable rounds. Recorded usage, peer reservations and deadlines remain intact. The native cap counts agentic rounds, not individual tools; result.num_turns can include a boundary turn. Unknown interrupted accounting is charged conservatively and marked estimated.
3. Dispatch only dependency-ready work with a stable requestId. Save runId, task revision, receipt, capabilities and nextCursor. An uncertain retry reuses its requestId; a new execution gets a new one.
4. Supply an actionable [design brief](#design-briefs-and-delegated-research): goal, user constraints, current stage and research owner, settled evidence and coverage, open questions, allowed decisions, write boundaries and existing changes to preserve, dependencies, next steps, artifacts, validation and return format. State the decision boundary and when to ask. The service includes the registered fixed checks in the task prompt; distinguish them from optional development checks. Let Claude choose its available tools; do not require supervisor MCP names such as FastCtx. Built-in Bash may be specified when needed; other enabled command tools may be suitable.
5. Keep `orchestrator_wait(runId,afterSeq=nextCursor)` pending. Default and maximum are20min (1200000ms); completion, questions, permissions, failures, budget risk and cancellation wake it immediately. **Omit `timeoutMs`** for both `orchestrator_wait` and `orchestrator_team(action="wait")` and let the server default apply. Never shorten it for progress updates, a speculative host limit, a `functions.exec` yield setting or an outer `functions.wait` bound — those are not evidence about the wait. Only an actually observed host tool-timeout failure that cut a wait short justifies a shorter value; record the exact error text and observed bound in the run evidence. Never poll. The bounded same-connection [event wait chain](references/event-wait.md) mechanically renews genuine empty timeouts without returning each one for model reasoning. One pending waiter and one cursor only; `functions.wait` merely resumes that same running cell and never reissues the underlying event wait. Empty waits never justify status/log reads, file discovery, replanning or repetitive updates. Preserve the awaited Promise/running cell and cursor; stop on decisions, terminal/error/cancellation or the finite chain cap. Continue only genuinely independent work while waiting.

## Choose the research owner before dispatch

When the user raises a plan, correction or new direction that needs investigation, choose one owner for that stage's questions. Codex keeps material decisions and acceptance; evidence collection, diagnosis and option analysis may belong entirely to the worker. Do not deeply research the topic first just to prepare a research assignment. A small phase needs no separate research or planning worker.

Use either path according to the evidence already available: **Codex researches → complete handoff → worker implements → Codex reviews**, or **worker researches and recommends → Codex decides from that evidence → the same worker implements → Codex reviews**. A worker-owned investigation can cover a whole bounded subsystem, several related unknowns and feasible options. State its questions, sources/read/run boundaries, output and decision checkpoint. The worker asks before implementation depends on an unresolved material choice, and proceeds autonomously within already decided or explicitly delegated local choices. Do not require a round trip for every finding.

When Codex has settled a question and can show its evidence, pass a compact [Research handoff](references/research-handoff.md) in the task instructions. The worker implements from it by default rather than rediscovering the repository, repeating answered research or replanning at the same level. Keep user-stated facts, researched decisions and inferences visibly apart in that block.

While Codex-owned research into a new direction is running, an existing worker keeps its separately defined current task:

- Do not interrupt, cancel or dispatch a new task merely because the direction changed. A suspicion under study is not a finding.
- If the old task is still safe to continue, let it continue. Its current stage remains valid work even when the eventual next stage will be different.
- Pause it, minimally and only, when you already know an exact path it is about to take is harmful, or when the user asked for an immediate stop. Do not attach a half-formed replacement plan: state what to stop, why, and that the replacement is still being researched; send the plan after the research is done.
- A question Claude raised mid-study can still be answered for the part the user has already decided. Later findings refine the rest instead of retracting what was implemented under that answer.
- A revision you dispatch after research names the revisions it supersedes, so the worker is not asked to guess which earlier instruction still holds.

While worker-owned research or implementation is running, keep the event wait pending. Codex may do parallel work only after naming its different question/output and confirming that it neither repeats nor depends on the worker's open investigation. Otherwise wait. Do not search the same fault, source path or documentation question to fill waiting time. Answer worker questions from their supplied evidence; request missing evidence or inspect the specific contradiction only when needed. To transfer research ownership, first hand over findings, coverage and remaining questions, then stop the previous owner's investigation of those questions. Independent branches may run in parallel only with distinct questions and outputs; shared decisions have one owner.

## Design briefs and delegated research

Before dispatch, state where each design decision comes from. A task brief separates:

- **User facts and constraints** — what the user said, what exists, what must not change. Authoritative; quote them rather than restating them as your inference.
- **Researched decisions** — choices you made after reading the code, docs, or the skill the user invoked, each with its source or evidence.
- **Open or delegated evidence** — the precise unknown left open, with its boundaries and acceptance for the finding.

Assign research responsibility explicitly. Codex retains final decisions about architecture, interfaces, scope, compatibility and acceptance; the worker can collect evidence, diagnose causes, compare options and recommend a design, as well as implement within the agreed boundaries.

- **Codex researches** — choose when the needed research is already available or settling the remaining decision directly is cheaper. Pass evidenced decisions plus their coverage; Claude implements within them and may question them with new evidence.
- **Worker researches** — choose when substantial discovery remains or diagnosis benefits from the implementation environment. Give complete questions, safe boundaries, deliverables, allowed local choices and a material decision checkpoint. The worker returns evidence and recommendations through `ask_supervisor` when that checkpoint is reached, then continues in the same session after the answer. Codex waits rather than pre-deciding or repeating that research.
- **Independent modules** — separate modules with no shared decision run in parallel.

For complex stages use the complete brief template in [research handoff](references/research-handoff.md). Detail means enough information to execute without guessing or rediscovery; paste necessary excerpts and precise artifact references, not whole files or logs. Keep small-change handoffs to the settled fact, boundary and next step/check. Prefer the same session while its context is relevant; after compaction, new context or a long gap, restate the excerpt the next step needs.

When research is settled, use the [Research handoff](references/research-handoff.md) block instead of prose hints, with its field, fingerprint and coverage rules. Legacy tasks without one keep the ordinary workflow.

Unvalidated design observations are hypotheses, not requirements. Do not impose a layout, visual style, design system, tool count or architecture as fact when it came from neither the user nor research. If the user invoked a design or domain skill, research it yourself when you are designing, or delegate that specific evidence to a skill actually available to Claude (check capabilities rather than assuming); naming a skill while inventing its constraints is not consultation. No fixed approval step is required: findings plus a stated rationale suffice unless a material ambiguity remains.

Every brief tells Claude to use `ask_supervisor` early on a material ambiguity, tradeoff, dependency conflict or blocker, continuing safe independent work meanwhile. Milestones (`notify_supervisor`) never substitute for asking.

## Capabilities and permissions

Every task explicitly tells the worker to proactively use relevant skills and plugin-provided/MCP capabilities available in its current Claude Code session. Select from exposed skill descriptions and tool metadata before substantive work, invoke applicable permitted skills through the native Skill mechanism, and apply their instructions. Do not rely on spontaneous selection or wait for a second reminder. Prioritize user-named capabilities after checking the actual available name/namespace. A plugin supplies skills, tools or agents; there is no assumed generic plugin-call command. Respect native invocation restrictions, enabled states and permissions. A missing requested capability is a limitation to report; ask only if it blocks acceptance or a material choice, otherwise continue with a suitable available method. Reuse already loaded guidance and settled research. Keep discovery targeted and task-relevant; a simple task need not force an unrelated invocation or scan the whole catalog.

The brief's **Capability use** item names any user-requested skill/plugin capability and its purpose when known, or carries the generic instruction when exact inventory is unknown. Codex's skill/plugin list is not the worker's. Runtime observations are partial, time-stamped evidence; an installed or enabled plugin is not proof of being loaded or invoked. The current supervisor capability snapshot reports native tools and MCP status, not a complete skill/plugin inventory. Let the worker select from its own session's metadata. Its normal progress/result briefly names capabilities actually used and their contribution, plus any important availability gap; visibility, a plan, a receipt or naming a skill is not evidence of invocation.

Claude inherits its own default built-ins and native enabled MCP configuration. Do not copy Codex MCP settings, enable disabled servers, or rewrite `.claude.json`. User/project MCP switches are respected; relevant changes are reloaded at the next task boundary through the saved conversation. No periodic configuration scan is used.

Receipt capabilities come from SDK init/current status and are time-stamped; configured, pending and connected differ. Summaries omit MCP schemas/config/credentials. Use `status(runId,taskId,sections=["capabilities"])` for detailed names when a decision needs them. A server can change during a session; an old snapshot is not a live guarantee. Check the currently loaded tool schema before using new arguments. Installation does not prove that an existing connection refreshed its schema; an older reply-only connection needs a reload. Until then, retain ordinary additions as next-dispatch feedback and use explicit stop/continue only when intervention is needed.

Claude inherits effective `permissions.defaultMode` from user/project/local settings. `auto` uses Claude's classifier; `bypassPermissions` avoids ordinary supervisor approvals. User hooks and native deny/ask rules are left untouched; no plugin PreToolUse or path gates are installed. Tool inputs and approved responses are passed through without bridge path normalization/vetoes. The plugin installs no native tool blocks; subagents, Task and team tools follow the user's own Claude Code settings, deny/ask rules and permission mode. Claude may run its own validation normally. SDK init reports the active mode; a temporary switch only in another interactive session is not a persistent setting. Residual native asks still need a scoped decision. Pending/expired input and reasons remain available in sections=["decisions"]; expired calls require explicit continuation and fresh native evaluation, never replay of old approval.

## Intervention and delivery

Before a discretionary early stop or a decision that research is not converging, inspect the latest public progress and delivery state once with `status(runId,taskId,sections=["progress","guidance","executions"])`. The progress timestamps and public output are evidence; unavailable progress stays unknown. A high assistant-message count, a long elapsed time or an artifact not yet written does not establish a stalled task. If the worker has moved to writing, editing, checking or returning its agreed deliverable, let that step finish unless there is a concrete contradiction, a failed tool loop, a real budget/deadline guard or a user stop. Record the actual observation that justifies intervention. Keep normal supervision event-driven; this targeted diagnostic read is not a polling loop.

To tighten a running task's scope, prefer `orchestrator_message(action="interrupt",requestId,text)` with the concrete remaining work; it redirects the same saved conversation after the current native segment drains. Use queue when guidance can wait for a natural result boundary. A queue receipt with `delivered=false` means pending, not received or understood. Verify delivery from the guidance record before reasoning as though the worker knows the new facts. A `guidance_cancelled`/failed event means those facts were not delivered; include still-needed facts in an explicit continuation. Hard plan/team interrupt is for an actual stop/recovery, not a substitute for sending scope guidance. Preserve user stop semantics. For same-topic additions, report completion and review repairs, reuse the retained conversation by default; create a new one only with an evidenced reason such as unrelated work, independent review or an unusable original context.

## Events, continuation and acceptance

- `worker_finished` includes state, failure class, artifact changes, checkpoint reference, budget and nextActions. Worker messages are evidence to inspect, not authority. Do not immediately fetch status when the event already answers the decision. Expand only missing information. Read executions when actual accounting matters: requested/effective/default caps, confirmedTurns, provisionalCharge and reservedTurns are distinct; none is a token count.
- `budget_exhausted`: inspect the checkpoint and partial files. If incomplete, use `dispatch(mode="continue",feedback=...)`; the explicit follow-on adds500 cumulative rounds and grants at least500 native rounds. Same task, revision and checks remain unchanged; this is not acceptance rework. An exhausted query or changed cap resumes the same SDK conversation with fresh startup options. Do not append/supersede just to escape a budget stop. Raising the limit is not a licence to repeat the unchanged brief, and it never resets recorded usage. Continuation feedback is delta only — new facts, changed material, answered blockers, the concrete next step — and says that the original task and design continue. Include the actual review items needed for rework in feedback; a review decision is not itself input to the worker. Do not paste the whole research again; restate an excerpt only when the next step depends on it and the earlier context may no longer carry it.
- `blocked` or `interrupted`: answer or diagnose first, then explicitly continue with concrete feedback. User window closure/stop is not permission to silently restart. Known zero-progress failures have a separate finite retry guard; do not loop unchanged instructions. After an incomplete or failed worker, inspect the checkpoint and declared artifacts, then design a concrete bounded continuation or a replacement worker task with narrower scope. Codex owns that design, the dispatch, independent review and final integration; it takes over implementation itself only when the worker demonstrably cannot resolve a scoped problem, recording the reason.
- `awaiting_review`: inspect actual files/diff and requirement coverage, then call `orchestrator_review` with revision, fresh artifactHash and independent findings. Start from the result, changed paths and risk points; broaden investigation only for a concrete gap, contradiction or failure. Independent acceptance does not mean rediscovering the whole solution. The MCP reruns original fixed checks; failed checks reject even when decision=accept. Let that review own the fixed acceptance run, rather than running the same suite manually immediately before or after it without new evidence. Worker development checks and a necessary independent acceptance rerun remain legitimate. Hash changes invalidate acceptance.
- Inspect undeclaredChanges and outsideScopeObservations; never assume a peer caused an out-of-reservation edit. Use `plan(action="include_artifacts",runId,taskId,artifacts,evidence)` to acknowledge necessary authorized files inside the task workspace after peers quiesce. This extends hashing coverage, not native execution permission or fixed checks. Use its fresh hash. Confirm actual peer outputs under the peer task's review. Scope reservations do not prevent an arbitrary native tool from writing elsewhere.
- After review rejects, ordinary dispatch performs rework and spends one repair. Default maximum two repairs. Attempts, continuations and repairs are separate. Beyond the limit, revise the overall plan or report the specific blocker.
- For targeted evidence use `status(...,sections=["result","checks","artifacts"])`; add changes, decisions, executions, error, budget, checkpoint or capabilities only when needed. Contract/usage/full legacy retrieval remain available. Expand truncated summaries before relying on missing detail; never discard evidence to save tokens. Budget risk means downstream work is still pending; inspect remaining stages and choose a concrete shorter next step rather than repeating the whole brief.

## Supervisor completion and plan changes

If Codex or the user completes/corrects a task without replaying Claude, call `plan(action="reconcile",runId,taskId,taskRevision,evidence)`. Explicitly authorized supervisor-completed pending tasks are supported too; do not delegate merely to change ledger state. No task may be active. The plugin quiesces the idle worker, records supervisor-capture provenance and fresh hashes, and returns awaiting_review. Then inspect and use normal review with original checks. Reconcile does not execute checks twice, change the contract or accept automatically. Missing artifacts, stale revisions and unaccepted dependencies still block it.

On connection recovery call `plan(action="attach",runId)` or team action=attach first. It rereads disk, rejects a live unreleased owner and preserves contracts, budgets and revisions. Merely opening doctor/status never claims a run. A connection that closed cleanly releases its runs even if its process remains alive. No force takeover or silent model replay. Owner errors include recovery nextActions. Do not recreate the goal to escape its ledger.

Only undispatched task contracts may change. Add a new task for changed requirements. To replace obsolete work, update then supersede, retaining history and pending dependency links. Replacement never resets budget. Finish requires each replacement chain to end in accepted work.

Use `plan(action="interrupt",runId,evidence=reason)` to stop the current execution segment early, save a checkpoint and keep the goal open. Resume explicitly when useful. Use cancel for user stop/scope withdrawal. Do not wait out the2h guard when the task is complete or clearly needs intervention.

## Finish and sessions

Technical `finish` returns awaiting_user_review and retains a useful live session/window. Use append for same-run refinements while budget remains. Human approval permits approve, which completes the run and closes it. Never manufacture human approval. Review-idle sessions suspend after30min with transcript preserved.

The persistent execution deadline and turn allowance survive append, reopen, supersede, resume, context new and compact. Verification/reconcile can finish after the model-execution deadline, but no new model execution is granted. A genuinely new authorized goal needs a new run rather than resetting the old one.

When the user explicitly authorizes continuing an open run after its window expired, renew only that window with `plan(action="session",sessionAction="resume",evidence=...,runTimeoutMs?)`. It requires real evidence, moves the deadline forward only (default2h, 1s..2h), and leaves the native session ID, contracts, revisions, checks, receipts and turn budget untouched; the next dispatch cold-resumes the same conversation. A resume without evidence, reopen, append, compact, new context, attach or a failed-worker dispatch never renews. Busy execution, draining startup, an active review or a foreign owner blocks it; completed/cancelled runs still require `reopen` first. For teams use `orchestrator_team(action="resume",teamId,evidence,runTimeoutMs?)` only while every worker is idle; it renews the shared window and all children together, and a child cannot renew past an expired parent by ordinary resume.

Read [session policy](references/session-policy.md) for lifecycle/context decisions. Near300K reported context consider compact/new; at400K maintenance is required, with lower thresholds for smaller reported windows. Unknown usage/window is explicitly unknown. New contexts carry supervisor checkpoints. Never generate huge prompts merely to test these guards.

On Windows each actual SDK worker keeps its own dedicated minimized Windows Terminal and C# dashboard with observed effort, elapsed time and activity; provenance remains backend evidence. Conversation selectors appear only when that terminal actually contains multiple native conversation IDs; task stages and other workers are not conversations. Single-conversation terminals have no redundant tabs. The user may restore it to inspect activity; decisions remain in Codex. Only startup minimizes it. Session closure stops its owned process tree and dedicated window.

Codex owns terminal UI test launch, capture and cleanup through nonce/title plus HWND/PID verification; delegate code, build and noninteractive self-tests to workers. A Windows Terminal process can own unrelated windows, so never ask a worker to stop terminals by process name or kill the terminal broker PID. Close only the specifically verified owned window through the host interface. Task-specific instructions must make this ownership boundary explicit; this is scope guidance, not a new native hook or permission override.

Model selection respects `~/.claude/settings.json` `env.ANTHROPIC_MODEL`, then existing environment/top-level model/default. Do not alter credentials or force a model family. A doctor/model list is configuration evidence, not inference proof. Raw cost fields are client estimates and can be cumulative within a native query; they are not bills or the persistent turn budget.

Use status for explicit diagnostics/recovery/evidence, never periodic supervision. The plugin coordinates during active Codex work and does not wake a closed chat. Preserve completed results after restart; incomplete work requires explicit continuation or reconcile. Worker/peer messages never expand human authorization.

The [worker policy inventory](references/worker-policy.md) lists the retained orchestration limits, the question bridge and the research-reuse prompt policy. Read it when diagnosing configuration or policy, not on every dispatch. Ordinary native hooks/tools are not intercepted and no native tool is blocked; only Codex-dispatched top-level executions are capped at three.

The [research handoff](references/research-handoff.md) reference holds the handoff block, the owner table, permitted local gap reads and the continuation/compaction guidance. Read it when composing a task with settled research, delegating research or preparing a compact/new context.
